# P06.3 — US-002: Authenticate and Leave the Account

**Version:** 1.0  
**Phase:** P06 — Incremental Implementation  
**Story:** US-002 / HU02 / MVP-002  
**Priority:** P0 — MVP Core  
**Canonical Epic:** EPIC-001 — Identity and Profile  
**User-supplied epic label:** ACCESS  
**Type:** User-story implementation prompt

## 1. Objective

Implement login and logout for the existing Notara account model. A registered
user must be able to sign in with the correct credentials, reach the
authenticated home/dashboard shell, receive a non-revealing error for invalid
credentials, and log out so that the server session is invalidated and the
browser returns to the public home screen.

Keep the implementation focused on US-002. Reuse the existing Django email
account, session, CSRF, React, and API foundations. Do not implement the full
score feed or any other story as part of the dashboard destination.

## 4. Story-Specific Acceptance Criteria

These criteria are required in addition to canonical P02 AC-003..AC-005.

### AC-US002-01 — Successful login

Given that I am a registered user, when I enter my correct credentials, then I
access my personal dashboard.

### AC-US002-02 — Invalid credentials

Given that I am a registered user, when I enter incorrect credentials, then
the system shows me an error message and does not allow access.

### AC-US002-03 — Logout

Given that I am authenticated, when I select the "Log out" option, then my
session ends and I am redirected to the public home screen.

## 5. Definition of Done

- Login with valid credentials works and opens the authenticated dashboard/home
  destination.
- Invalid credentials show a clear error without revealing whether an email
  address is registered or exposing sensitive details.
- Logout invalidates the server-side session; subsequent protected API access
  is denied and the browser reaches the public home screen.
- The flow is verified at mobile and desktop sizes. Use the P02/P04 browser and
  viewport matrix where available and report actual coverage.
- Product Owner approval is complete only when actual approval evidence is
  recorded. Otherwise keep it `PENDING`.
- Automated tests, build checks, browser checks, and limitations are recorded
  honestly in the implementation log.

## 6. Existing Implementation and Scope Boundaries

P06.2 added an email-based custom Django user, registration endpoint,
`GET /api/me/`, CSRF-token endpoint, React registration page, and minimal
session-aware home page. Inspect the live code before editing; use the actual
model and URL conventions present there.

### Included

- Visitor login screen and accessible form with email and password.
- Django authentication against the existing registered-user model.
- Server-side login endpoint that establishes the Django session.
- Authenticated dashboard/home state using existing identity data.
- Visible authenticated "Log out" action.
- Server-side logout endpoint that invalidates the session.
- Public home/login navigation after logout.
- Focused backend and frontend tests for access boundaries and the story.

### Excluded

- Registration changes, profile management, password change/recovery,
  differentiated roles, email verification, social login, or score/feed,
  filtering, publication, likes, or comments.
- Implementing the full US-007 dashboard/feed. The authenticated destination
  for this story may be a clear minimal dashboard shell using the existing home
  screen; score discovery remains a later story.
- Storing credentials or bearer tokens in local storage/session storage.
- Adding an auth framework, routing framework, or generalized state layer
  unless the current code demonstrably requires it.

## 7. Technical and Security Requirements

### 7.1 Backend authentication

- Use Django's `authenticate()` and `login()` with the existing email-based
  `accounts.User`; do not duplicate credential comparison or password hashing.
- Accept only the required login credentials and return the minimal safe user
  identity needed by the existing UI.
- Return the same generic authentication error for an unknown email and an
  incorrect password. Never reveal account existence, password state, hashes,
  stack traces, or internal database details.
- Keep failed login attempts unauthenticated and ensure they do not create or
  mutate account/session state.
- Implement logout as an authenticated, CSRF-protected `POST`, call Django's
  `logout()` to flush the server-side session, and return a clear success
  response. Do not implement logout as a state-changing GET.
- Preserve current CSRF middleware and same-origin session-cookie behavior.
  Do not disable CSRF or put credentials/tokens in browser storage.
- Ensure `GET /api/me/` returns `401` after logout and remains useful as the
  authoritative session check. Protect the dashboard/server endpoints rather
  than trusting client-only state.

### 7.2 Frontend behavior and editability

- Keep login UI in a dedicated, clearly named component/page and authentication
  requests in the existing small API module or a similarly clear auth helper.
- Use the existing React + TypeScript stack, minimal route selection already
  present, and semantic labeled inputs. Avoid adding a routing dependency only
  for login/logout unless justified and recorded.
- Add a public login route/link and a visible logout control when authenticated.
  On successful login, navigate to the authenticated dashboard/home shell.
  On successful logout, clear client user state and navigate to public home.
- If logout fails, do not claim the session ended; show a clear recoverable
  message and retain/recheck session state.
- Handle loading, invalid credentials, API/network errors, already-authenticated
  visitors, and logout-in-progress state. Clear the password after failed
  submission and never log it.
- Keep UI code and styles simple and separately editable by the frontend team.
- Preserve same-origin local development through the existing Vite `/api`
  proxy and include cookies/CSRF token on unsafe requests.

### 7.3 API path and architecture note

The architecture describes `/api/v1/auth/login` and
`/api/v1/auth/logout`, while the existing US-001 implementation uses local
paths under `/api/` without the version segment. Inspect current routing and
avoid an unrelated API-wide migration in this story. Follow the established
working route convention for the new login/logout endpoints, document this
existing architecture deviation in the implementation log, and leave any
version-prefix migration for an explicit architecture/API-contract change.

   desktop viewport widths, and run frontend type/build checks. Use Chrome,
   Edge, Firefox at 360/768/1280 px when available; report exact coverage.

   authorization, state-changing GET, token storage, or unrelated story work.

   `artifacts/06_implementation/IMPLEMENTATION_LOG.md` and update
   `artifacts/06_implementation/PROMPT_LOG.md`, preserving prior entries.
