# P06.1 — Implementation Foundation

**Version:** 1.0
**Phase:** P06 — Implementation
**Type:** Code generation
**Execution mode:** One-time technical foundation setup

## 1. Objective

Implement the technical foundation of the approved software architecture in the current repository.

The goal is to transform the approved architecture into a coherent, executable, maintainable project structure that is ready for incremental feature development.

The implementation may include:

* Project and module structure.
* Framework and runtime configuration.
* Application entry points and startup configuration.
* Shared infrastructure and common components.
* Persistence configuration and database connection foundations.
* API routing and application-layer foundations, when required by the approved architecture.
* Frontend application foundations, when applicable.
* Environment configuration and configuration examples.
* Logging and error-handling foundations.
* Security foundations appropriate to the architecture.
* Health checks or equivalent mechanisms to verify application startup, when appropriate.
* Extension points required to implement future user stories without restructuring the project unnecessarily.

**This phase establishes the technical foundation only. It must not implement the business functionality of individual user stories.**

## 2. Required Inputs

Read and use the following sources:

1. `prompts/system/SYSTEM_PROMPT.md`
2. `artifacts/05_architecture/ARCHITECTURE.md`
3. `artifacts/05_architecture/ARCHITECTURE_VALIDATION.md`
4. `artifacts/03_planning/PRIORITIZATION.md`
5. `artifacts/03_planning/product_backlog.json`
6. `artifacts/04_ux/UX_SPEC.md`
7. `artifacts/04_ux/UX_SPEC_VALIDATION.md`
8. The current repository structure, source code, configuration files, and relevant documentation.

If any required artifact is missing, unreadable, or inconsistent with another authoritative artifact, record the issue and determine whether implementation can safely proceed.

The architecture and its validation report are the primary references for technical decisions. Planning and backlog artifacts provide context about the expected product scope and future implementation needs. UX artifacts provide relevant structural and integration constraints.

Do not treat planning or backlog artifacts as authorization to implement user stories during this phase.

## 3. Preconditions and Blocking Conditions

Before modifying the repository:

1. Confirm that the architecture document exists and has been validated.
2. Review `ARCHITECTURE_VALIDATION.md` for its final status, unresolved conditions, and blockers.
3. Identify unresolved decisions that materially affect the foundation.
4. Inspect the existing repository to determine whether a foundation already exists and whether it should be extended rather than replaced.

If the architecture is not approved, its validation contains unresolved critical blockers, or a missing decision prevents a safe implementation, do not proceed with the affected implementation.

Use `BLOCKED` when the foundation cannot be implemented responsibly. Explain the blocking issue and the evidence supporting it.

Do not silently convert an unapproved proposal into an approved technical decision.

## 4. Implementation Boundaries

### 4.1 Included

Implement only what is necessary to establish the approved technical foundation.

Examples include:

* Creating the agreed directory and module structure.
* Configuring the selected framework, runtime, build system, and dependency management.
* Establishing application startup and entry points.
* Configuring database access and persistence infrastructure without implementing story-specific business operations.
* Creating shared API, frontend, or service-layer foundations when required.
* Establishing environment variable handling and safe configuration defaults.
* Creating example environment configuration files where appropriate.
* Configuring shared logging, exception handling, and security mechanisms.
* Providing minimal health checks or equivalent startup verification where appropriate.
* Documenting how to configure, run, and inspect the foundation.

### 4.2 Excluded

Do not implement:

* Individual user stories or their acceptance criteria.
* Story-specific business workflows.
* Complete domain features or user-facing functional flows.
* Business rules that belong to a particular user story.
* Seed data or mock behavior that implies real product functionality, unless explicitly required by the approved architecture for technical verification.
* Unapproved architectural changes or additional infrastructure.
* Placeholder modules, abstractions, endpoints, screens, or services that do not serve an identified foundation requirement.

Do not implement a user story merely because its future implementation depends on a particular module or component. Create only the technical foundation needed to support that future work.

If a foundation component requires a minimal technical verification mechanism, keep it isolated, clearly identify its purpose, and avoid presenting it as completed product functionality.

## 5. Implementation Principles

Follow these principles throughout the work:

1. **Architecture conformance:** follow the approved architecture and document any justified deviation.
2. **Minimal sufficient foundation:** implement the smallest coherent foundation that supports the planned incremental development.
3. **Consistency:** follow the existing repository conventions and established patterns unless there is a documented reason not to.
4. **Maintainability:** prefer clear module boundaries and understandable configuration over unnecessary abstractions.
5. **Security by default:** do not commit credentials, secrets, private keys, or environment-specific sensitive values.
6. **Traceability:** connect significant implementation decisions to the relevant architecture sections or other authoritative artifacts.
7. **No invented requirements:** do not silently introduce product behavior, dependencies, infrastructure, or technical decisions not supported by the approved sources.
8. **Existing code preservation:** inspect existing files before replacing them. Preserve valid work and modify only what is necessary.
9. **Reproducibility:** document the commands and configuration needed to install dependencies, start the application, and verify the foundation.
10. **Honest verification:** report only checks that were actually executed and distinguish verified results from assumptions or unverified expectations.

If a technical detail is unspecified but does not block implementation, use the least consequential reasonable choice, record it as an assumption, and explain its impact. Do not use an assumption to bypass a required approval or resolve a material architectural decision without authorization.

## 6. Execution Process

### Step 1 — Inspect the repository and inputs

* Read all required artifacts.
* Inspect the current project structure, source code, dependency manifests, configuration, and documentation.
* Identify the foundation components required by the architecture.
* Identify existing components that can be reused.
* Record missing inputs, inconsistencies, assumptions, and unresolved decisions.

### Step 2 — Define the foundation scope

Identify the specific technical components to implement and map each one to its architectural justification.

Do not create a new product backlog or re-plan the sprint. Use the existing planning artifacts only to understand the future product scope and avoid creating a foundation that prevents its implementation.

### Step 3 — Implement the foundation

* Modify or create the necessary files.
* Configure the agreed application components and shared infrastructure.
* Integrate the components sufficiently for the application to start or for the relevant foundation checks to run.
* Follow the approved architecture and repository conventions.
* Avoid implementing story-specific functionality.

### Step 4 — Run available verification checks

Run the relevant checks supported by the repository and environment, such as:

* Dependency installation or dependency consistency checks.
* Compilation, build, or static checks.
* Application startup.
* Database connectivity or configuration checks, when feasible.
* Health checks or equivalent technical verification.
* Existing automated checks relevant to the modified foundation.

Do not claim a check passed if it was not executed. If a check cannot be run because of missing credentials, unavailable infrastructure, or environment limitations, document the reason and the exact limitation.

### Step 5 — Review the implementation

Before completing the phase, verify that:

* The foundation is consistent with the approved architecture.
* The application structure is coherent and can support incremental development.
* No user story has been implemented inadvertently.
* Configuration and secrets are handled safely.
* Required setup and verification instructions are documented.
* All material assumptions, deviations, and unresolved issues are recorded.

### Step 6 — Create the implementation log

Create or update:

`artifacts/06_implementation/IMPLEMENTATION_LOG.md`

The log must describe the foundation that was actually implemented, the decisions made, the checks executed, and the remaining limitations.

## 7. Required Output: IMPLEMENTATION_LOG.md

The implementation log must contain the following sections.

### 7.1 Metadata

Include:

* Phase and prompt identifier.
* Version.
* Execution date, if available.
* Implementation status.
* Repository or project context, when known.
* References to the input artifacts used.

### 7.2 Executive Summary

Summarize:

* What foundation was implemented.
* The current state of the repository.
* Whether the application or relevant foundation components can be started or verified.
* The most important limitations or outstanding items.

### 7.3 Implemented Components

For each significant component, document:

* Component or module.
* Purpose.
* Relevant files or paths.
* Corresponding architecture section or requirement.
* Implementation outcome.

### 7.4 Repository Changes

List the relevant files created, modified, or removed and briefly explain why each change was necessary.

Avoid listing generated files or trivial changes individually when a concise grouped description is clearer.

### 7.5 Architectural Conformance and Deviations

Document:

* How the implementation follows the approved architecture.
* Any deviations.
* The reason and impact of each deviation.
* Whether the deviation requires approval or architectural document updates.

Never present an unapproved deviation as if it were already accepted.

### 7.6 Configuration and Execution Instructions

Describe, as applicable:

* Prerequisites.
* Dependency installation.
* Environment configuration.
* Database or external service configuration.
* Commands to build and run the application.
* Commands to perform relevant technical checks.

Do not include real credentials or secrets.

### 7.7 Verification Results

For each executed check, include:

* Check name.
* Command or procedure.
* Result.
* Relevant evidence or output.
* Failure details, if applicable.

Use explicit distinctions between `PASSED`, `FAILED`, `NOT_RUN`, and `BLOCKED`.

### 7.8 Assumptions and Unresolved Issues

List each relevant assumption, unresolved decision, limitation, or dependency.

For each item, state:

* Description.
* Reason it remains unresolved.
* Impact on the foundation.
* Whether further approval or action is required.

### 7.9 Scope Boundary

Explicitly confirm whether story-specific functionality was excluded.

If any story-specific behavior was added inadvertently or was unavoidable for technical verification, identify it and explain why.

### 7.10 Handoff to Foundation Validation

Provide the information needed by P06.2 to inspect the repository, including:

* Main files and modules to review.
* Commands used for verification.
* Checks that could not be executed.
* Important assumptions and deviations.
* Known risks and outstanding issues.

### 7.11 Final Status

Choose exactly one status:

* `READY` — the foundation has been implemented and relevant available checks support readiness for foundation validation, with no material unresolved assumptions affecting readiness.
* `READY_WITH_ASSUMPTIONS` — the foundation is implemented, but one or more documented assumptions or limitations remain that do not prevent foundation validation.
* `BLOCKED` — a material blocker prevents responsible implementation or leaves the foundation in an unusable or unsafe state.

The status is a statement from the implementation process, not independent approval. P06.2 must verify it against the actual repository.

## 8. Self-Validation Checklist

Before finalizing the log, confirm:

* [ ] Required input artifacts were inspected.
* [ ] Architecture approval and blocking conditions were checked.
* [ ] The repository was inspected before making changes.
* [ ] Implemented components are justified by the approved architecture.
* [ ] No user stories or story-specific acceptance criteria were implemented.
* [ ] Existing valid code was preserved where appropriate.
* [ ] Configuration does not expose secrets.
* [ ] Relevant verification checks were executed or explicitly marked as not run.
* [ ] Deviations, assumptions, and unresolved issues were documented.
* [ ] Setup and execution instructions reflect the actual implementation.
* [ ] `IMPLEMENTATION_LOG.md` accurately represents the current repository state.

## 9. Pipeline Transition

P06.1 is complete when the implementation log has been produced and the foundation is ready for independent validation.

**Do not proceed directly to user-story implementation solely because this prompt reports `READY` or `READY_WITH_ASSUMPTIONS`.** P06.2 must validate the foundation first.

* If P06.2 returns `PASS`, the foundation may be used for incremental user-story implementation.
* If P06.2 returns `PASS_WITH_WARNINGS`, proceed only when the remaining warnings do not prevent safe incremental development and any required conditions are satisfied.
* If P06.2 returns `FAIL`, correct the identified issues and repeat the relevant implementation and validation steps.
* If P06.2 returns `BLOCKED`, resolve the blocker before proceeding.

P06.1 and P06.2 establish and validate the technical foundation. They do not replace incremental story implementation, story-level validation, or the later product-testing phase.
