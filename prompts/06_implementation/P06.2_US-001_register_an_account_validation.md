## 3. Preconditions and Blocking Conditions

Before testing:

- Confirm that registration behavior has actually been implemented. A prompt,
  plan, report template, placeholder screen, disconnected endpoint, or mock
  persistence is not an implementation.
- Inspect the complete request path from the React form through the Django
  endpoint and configured database to session state and post-registration
  navigation.
- Review the implementation log against the actual changed files and test

- Confirm whether migrations can be applied safely to the available database.

If the feature is not implemented, set execution status to `NOT_RUN` and overall

## 4. Validation Scope

### Included

- Visitor registration UI for name, email, and password.
- Required-field, email-format, duplicate-email, and minimum-eight-character
  password validation on both client and server where applicable.
- Persistent account creation using the configured Django ORM/database.
- Database-level uniqueness protection for normalized email addresses.
- Password hashing and non-disclosure of passwords/password hashes.
- Establishment of an authenticated Django session on successful registration.
- Navigation to a home destination that actually reflects authenticated state.
- CSRF/session integration and public-versus-authenticated access boundaries.
- Registration-focused tests, frontend build/type checks, and responsive
  browser verification.
- Implementation-log accuracy and Product Owner review status.

### Excluded

Do not approve or expand this validation to cover profile management, login or
logout as standalone stories, password changes, account recovery, email
verification, social login, score publishing, or unrelated product features.
Only inspect adjacent behavior when needed to prove US-001 session setup and
home navigation.

## 5. Acceptance Criteria and Evidence

### 5.1 Supplied US-001 criteria

| ID | Expected behavior | Minimum evidence |
|---|---|---|
| AC-US001-01 | Valid name, email, and password create one account, establish an authenticated session, and navigate to the home screen. | Backend test verifies persisted account and authenticated session; frontend/integration test verifies successful navigation and authenticated state. |
| AC-US001-02 | A registered email is rejected with a clear message and no duplicate account. | Test submits the same normalized email again, verifies field-level feedback and unchanged account count; include case/whitespace normalization if implementation accepts it. |
| AC-US001-03 | Empty required fields, malformed email, and password shorter than 8 characters are rejected with clear messages and no account. | Backend tests for each invalid case, including 7-character rejection and 8-character acceptance; frontend tests/manual evidence for visible errors. |

All authoritative validation must occur on the server. A client-only test does
not satisfy these criteria.

### 5.2 Canonical P02 criteria

Also verify that implementation satisfies canonical AC-001 and AC-002: valid
approved registration data creates an account or returns a clear validation
result; invalid/incomplete data does not create an account and identifies the
required correction.

## 6. Detailed Review Checklist

### 6.1 Functional and data integrity

- Submit valid data through the real registration flow and verify the account
  is persisted in the configured database.
- Verify exactly one account is created and the response does not disclose
  sensitive account fields.
- Submit duplicate email variants consistent with the documented
  normalization policy. Verify the database constraint prevents duplicates,
  including under a concurrent or race-condition test when feasible.
- Verify blank/whitespace-only name, blank email, malformed email, blank
  password, and password lengths 7 and 8 at the API boundary.
- Verify rejected submissions leave no partial account or session side effects.
- Verify a successful registration authenticates the new user and redirects to
  the home destination; verify the destination behaves as authenticated.
- Verify a failed submission stays on registration, identifies corrections,
  and does not expose stack traces or database details.

### 6.2 Security and persistence

- Confirm passwords are stored through Django password hashing and cannot be
  recovered from responses or logs.
- Confirm email normalization and uniqueness rules are consistent between
  application validation and database constraints.
- Confirm the account model and migrations use the configured environment-based
  database connection and are suitable for PostgreSQL.
- Confirm migrations are non-destructive and apply cleanly to a fresh test
  database; review impact on existing users/database state if applicable.
- Confirm registration remains public but authenticated home/protected access
  depends on a valid session.
- Confirm session cookies and CSRF behavior follow Django's configured
  protections; do not accept disabled CSRF as a passing shortcut.
- Check rate limiting only if already established by approved code or policy;
  do not invent a new requirement in this validation.

### 6.3 Frontend maintainability and responsive behavior

- Confirm the registration form is separated into understandable components
  and does not make the app entry point a monolith.
- Confirm API calls/types are easy for the frontend team to locate and edit.
- Confirm semantic labels, keyboard access, visible field errors, and
  accessible submission feedback.
- Verify the form at 360 px, 768 px, and 1280 px in current Chrome, Edge, and
  Firefox when those environments are available. Record browser/version,
  viewport, procedure, and result. Do not claim the full matrix from a single
  browser or viewport.
- Confirm the page does not overflow or obscure fields, errors, submit control,
  or navigation at narrow widths.

### 6.4 Implementation log and approval

Confirm the P06.2 log entry:

- matches the actual code, migrations, test results, and changed files;
- identifies the story-specific criteria and canonical traceability;
- records exact verification commands and honest outcomes;
- records known source differences between the provided criteria and P02/P04;
- leaves Product Owner review `PENDING` unless approval evidence is present.

A reviewer must not infer Product Owner approval from generated text, a passing
test suite, or this validation report.

## 7. Source Alignment Review Gate

The supplied criteria differ from the current upstream source:

- P02 does not explicitly define name/email fields, unique-email behavior, or
  an eight-character minimum password.
- P04 FLOW-001 says successful registration continues to login; the supplied
  criterion requires an authenticated session and redirect to home.
- P05 validation identifies registration fields and password policy as
  unresolved pending confirmation.

Validate behavior against the explicit criteria supplied for this story, and
record these deltas as a review gate. Do not modify upstream artifacts as part
of validation. If the implementation claims the canonical upstream artifacts
were unchanged and fully aligned, report that claim as inaccurate. Product
Owner approval remains a separate DoD item.

## 9. Severity and Result Rules

Severity levels:

- **CRITICAL:** unsafe credential handling, duplicate persistent accounts,
  unauthenticated access incorrectly granted, or data loss.
- **HIGH:** a supplied acceptance criterion fails, persistence/session behavior
  is broken, or a critical migration/security boundary is invalid.
- **MEDIUM:** material usability, responsive, traceability, or verification gap
  with a bounded workaround or review gate.
- **LOW:** minor maintainability/documentation issue with limited impact.

Choose exactly one final result:

- **PASS:** all supplied and canonical acceptance criteria pass with direct
  evidence; security/data checks pass; required responsive checks are complete;
  no material findings remain. Product Owner approval is separately evidenced
  before claiming DoD complete.
- **PASS_WITH_WARNINGS:** core criteria pass, but there are non-blocking
  verification gaps, open source-alignment decisions, or external review gates.
- **FAIL:** implementation exists but one or more material acceptance criteria,
  security checks, or data integrity checks fail.
- **BLOCKED:** implementation cannot be reliably tested due to missing
  implementation, unavailable required dependencies/database, unsafe migration
  uncertainty, or another concrete blocker.
