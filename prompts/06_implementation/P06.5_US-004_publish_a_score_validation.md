## 3. Preconditions and Blocking Conditions

- Locate a traceable decision selecting text-only, image-only, or dual-mode.
- Confirm requirements/architecture artifacts were updated if the decision
  changes the approved text-only/image-excluded MVP.
- Confirm the implementation matches exactly one approved content contract;
  never infer an unrecorded hybrid.
- Confirm the created score is persisted and discoverable via the feed
  integration, not merely shown in frontend state.

If the content model is unresolved, set execution to `NOT_RUN`, overall result
`BLOCKED`, and explain that implementation cannot be validated against a single

If the feature is absent, report validation as pending. Mark unavailable checks
`NOT_RUN` and do not claim them passed.

## 5. Detailed Review by Content Decision

### 5.1 Common publication invariants

- Mutation requires an authenticated session and valid CSRF token.
- Owner is derived from the server session; client cannot assign ownership.
- Title and instrument are required; description remains required while
  canonical FR-005/BR-006 are in force.
- Invalid requests do not create a publication, partial row, or orphan file.
- A successful record is persisted and available from the community-feed
  contract; do not require the full US-007 filters/pagination implementation
  unless already available.

### 5.2 If text-only is approved

- Accept `.abc` and plain text only; reject JPG, PNG, PDF, and other formats.
- Enforce non-empty textual content and the 1,000-character maximum.
- Validate `.abc` fields `X:`, `T:`, `M:`, `L:`, `K:` and the approved valid
  musical-line condition; do not claim advanced ABC grammar support.
- Verify display preserves line breaks and distinguishes content format.
- Mark supplied JPG/PNG ACs as superseded/not satisfied by the approved scope
  decision; do not misreport them as passed.

### 5.3 If image-only is approved

- Accept only actual JPG/PNG image content and reject PDF/other formats.
- Verify content signature/decoder format, extension agreement, configured
  size cap, safe storage, and authenticated access policy.
- Verify image path metadata is persisted, bytes are in configured storage, and
  no failed submission leaves orphaned files.
- Report that P02 textual content/ABC requirements are changed/superseded only
  if approved source artifacts show that change.

### 5.4 If dual-mode is approved

- Test all canonical text cases and the JPG/PNG cases independently.
- Verify each saved publication clearly identifies its content mode.
- Verify PDF/unsupported files are rejected and text-only records remain valid.
- Confirm the approved schema/API/storage supports both modes without
  overloading fields or losing format traceability.

## 6. Security, Persistence, and Responsive Review

- Verify anonymous requests are denied and CSRF is enforced on publication.
- Verify all data persists through Django ORM/database migrations.
- For files, verify configured storage, authenticated access as approved,
  content validation, safe response headers, and replacement/failure cleanup.
- Verify no secrets, internal errors, unsafe HTML rendering, or user-supplied
  owner IDs are exposed/trusted.
- Test actual publication flow at mobile and desktop viewports; report browser,
  version, viewport, and evidence. Target current Chrome, Edge, and Firefox at
  360/768/1280 px when available.

## 8. Result Rules

- **PASS:** one approved content contract is implemented; its relevant
  acceptance criteria, persistence/feed visibility, security, and required
  verification pass; no material findings remain.
- **PASS_WITH_WARNINGS:** approved core behavior passes but non-blocking browser,
  storage, or external-review gates remain.
- **FAIL:** implementation exists but violates an approved criterion or
  integrity/security check.
- **BLOCKED:** content model is unresolved, implementation is absent, or a
  concrete prerequisite prevents reliable validation.

Severity: CRITICAL (unauthorized access/data exposure), HIGH (publication,
format or persistence failure), MEDIUM (scope, accessibility, or verification
gap), LOW (minor documentation/maintainability issue). Keep Product Owner
approval and all unrun checks explicit; never report assumptions as passes.
