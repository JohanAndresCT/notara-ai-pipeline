# P06.4 — US-003: Manage Profile Information

**Version:** 1.0  
**Phase:** P06 — Incremental Implementation  
**Story:** US-003 / HU03 / MVP-003  
**Priority:** P1 — MVP Supporting  
**Canonical Epic:** EPIC-001 — Identity and Profile  
**User-supplied epic label:** ACCESS  
**Type:** User-story implementation prompt

## 1. Objective

Implement an authenticated profile experience using the existing Notara
Django/React account foundation. The user can view and update their name and
main instrument, upload a JPG/PNG profile photo, and change their password as
required by canonical P02 US-003. Changes must persist and the updated profile
must be visible immediately.

Keep the profile UI and API easy to edit. Store image files through Django's
swappable storage interface, not as database blobs, so local storage can be
replaced by the team's production media storage without changing profile
business logic.

## 4. User-Supplied Profile Acceptance Criteria

Implement the following requested criteria in addition to canonical P02
AC-006..AC-008.

### AC-US003-01 — View current profile

Given that I am authenticated, when I access "My profile", then I see my
current data: name, photo, and main instrument.

### AC-US003-02 — Update name or instrument

Given that I am on my profile, when I update my name or instrument and save the
changes, then the changes persist and are reflected immediately.

### AC-US003-03 — Upload profile photo

Given that I update my profile photo, when I upload a valid JPG or PNG image,
then the new photo replaces the previous one on my profile.

## 5. Definition of Done

- Authenticated user can view/update name and main instrument and can upload a
  JPG/PNG profile photo.
- Changes persist in the configured database/storage and appear immediately in
  the profile view.
- Non-JPG/PNG, malformed image data, and over-limit uploads are rejected
  server-side with clear feedback and no profile change.
- Canonical P02 password-change behavior remains available; invalid or
  incomplete password-change input does not change the password.
- Profile flow is verified on mobile and desktop; report exact browser and
  viewport coverage.
- Product Owner approval is marked complete only with actual evidence;
  otherwise it remains `PENDING`.

## 6. Source Alignment and Review Gates

This request is more specific/different than approved upstream scope:

- P02 FR-003 names username, name, description, and main instrument; P02
  US-003/FR-004 also includes password change.
- The user-supplied profile criteria add a photo but do not request username or
  description.
- P03 lists image uploads as `OOS-003`; P05 describes a text-first MVP with no
  image storage. The current user explicitly requests profile-photo behavior.

Implement the expressly requested photo/name/instrument behavior and retain
canonical password change. Do not silently edit P02/P03/P04/P05. Record the
photo scope expansion and username/description differences as review gates in
the implementation artifact and validation report. Product Owner approval
remains pending until evidence is recorded.

Do not invent extra product constraints. To prevent unbounded local uploads,
use a configurable default maximum of 5 MiB (`PROFILE_PHOTO_MAX_BYTES`); record
this as a technical safeguard requiring Product Owner confirmation. Accept only
`.jpg`, `.jpeg`, and `.png` filenames whose decoded image format is JPEG or PNG.
Do not trust the client MIME type or extension alone.

## 7. Implementation Boundaries

- An authenticated `My profile` page linked from the authenticated home.
- Profile read/update using the current user's session identity only.
- Name and main instrument persistence; an editable description is not added

- JPG/PNG upload with server-side content validation and a size safeguard.
- A protected image-read endpoint or equivalent access-controlled media path.
- Canonical password-change flow required by P02 US-003/FR-004.

### Excluded

- Saving image bytes in the relational database or hardcoding a cloud vendor.
- Unrelated score feed, publishing, or community workflows.

## 8. Technical Requirements

### 8.1 Authentication and authorization

- Require the existing Django session for profile read/update, password change,
  and photo retrieval. Return 401 for anonymous requests.
- Derive the account from `request.user`; never accept a user ID from the client
  as authority to update a profile.
- Require CSRF for unsafe session-authenticated requests.
- Keep email read-only; do not change authentication identity as part of this
  story.

### 8.2 Profile data and media storage

- Add only fields needed by this request to the existing custom user model:
  `main_instrument` and optional `photo` (plus any strictly necessary metadata).
- Use a Django `ImageField` and checked-in migration. Add Pillow as a pinned
  backend dependency and validate actual file contents with it.
- Store media under configurable `MEDIA_ROOT` using Django's storage API. Make
  the storage backend configurable via environment so a production backend can
  replace local file storage without changing model/view code.
- Keep local uploaded files out of Git. The relational database stores the
  image path/metadata, not the image bytes.
- When replacing a photo, remove the previous stored file only after the new
  photo and profile update succeed; failed validation must preserve the old
  profile and photo.
- Do not expose the upload directory as an unauthenticated static directory.
  Serve the current user's photo through an authenticated endpoint or an
  equivalent reviewed access-control mechanism.
- Verify image decoding, file extension, allowed format, and configured size
  limit on the server. Handle invalid image bytes without returning a traceback.

### 8.3 Profile and password API

- Reuse the existing `/api/me/` convention. GET returns safe current-user
  profile fields; PATCH accepts multipart form data for profile/photo updates.
- Return the updated profile in the successful PATCH response so the client
  can reflect changes immediately without an unnecessary page reload.
- Provide a CSRF-protected password-change POST under the current API
  convention. Verify current password, reject missing/invalid input, use Django
  password hashing, and preserve the authenticated session after a successful
  password change.
- Do not return password or password hash. Use clear field-level errors.

### 8.4 Frontend

- Add a small, clearly named profile page/component and API functions; keep
  presentation, request logic, and storage concerns separate and replaceable.
- Show current name, main instrument, and photo; use a file input accepting JPG
  and PNG; show selected image preview and upload/update feedback.
- Include canonical password-change controls in a separate section.
- Handle loading, save, validation, upload, and network errors; preserve
  existing profile values after failure.
- Keep form labels, keyboard access, and feedback accessible. Use the existing
  responsive style conventions and avoid a new UI/router dependency.
