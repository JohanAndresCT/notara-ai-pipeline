# P06.5 — US-004: Publish a Score

**Version:** 1.0  
**Phase:** P06 — Incremental Implementation  
**Story:** US-004 / HU04 / MVP-004  
**Priority:** P0 — MVP Core  
**Canonical Epic:** EPIC-002 — Score Publication and Ownership  
**User-supplied epic label:** CONTENT  
**Type:** User-story implementation prompt

## 1. Objective

Implement authenticated score publication so a user can provide score content,
required metadata, publish it, and have the resulting publication available to
the community feed. Keep the implementation within the approved US-004 scope
and make the create form, backend validation, persistence model, and storage
integration straightforward for the frontend and database teams to extend.

**Do not begin code changes until the content-format decision gate in Section 6
is resolved and recorded.** The current request describes a text-format story
but specifies JPG/PNG uploads as the accepted score content. P02/P03/P05 define
textual `.abc`/plain-text scores and explicitly exclude image uploads. These
are materially different content models; this prompt must not silently invent
a hybrid.

## 4. User-Supplied Acceptance Criteria

These criteria were supplied for this requested story and must be reconciled
with the canonical criteria before implementation.

### AC-US004-01 — Publish JPG/PNG score to the community

Given that I am authenticated, when I upload a JPG or PNG image, complete the
title and instrument, and publish, then the score appears in the community
feed.

### AC-US004-02 — Reject unsupported file types

Given that I try to upload a PDF or another unsupported format, then the system
rejects the file and indicates the valid formats.

### AC-US004-03 — Require title and instrument

Given that I leave the title or the instrument blank, then the system does not
allow publication and shows the corresponding error.

The story statement also asks for a textual score and description. Canonical
BR-006 requires title, instrument, description, and textual content. Do not
remove description or textual-content requirements without recording the
approved scope decision.

## 6. Required Content-Format Decision Gate

The current sources conflict:

- **P02/P03/P05 approved MVP:** score content is text (`.abc` or plain text),
  up to 1,000 characters; image uploads are excluded as `OOS-003`.
- **User-supplied AC:** JPG/PNG are accepted score uploads and PDF/other files
  are rejected.
- **User story wording:** calls the upload a score “in text format,” while the
  image criteria describe binary image content.
- **Feed dependency:** P04/US-007 owns the full community feed. US-004 must make a
  created publication available to the existing/feed contract, but must not
  implement unrelated filtering, pagination, detail interactions, likes, or
  comments.

Before writing implementation code, require a traceable Product Owner/content
model decision selecting exactly one behavior:

1. **TEXT_ONLY — Text-only:** follow approved P02/P05 formats `.abc` and plain text; reject
   JPG/PNG and PDF. This does not satisfy the supplied image-upload ACs.
2. **IMAGE_ONLY — Image-only:** accept JPG/PNG score images and reject PDF/other files. This
   replaces the canonical textual content rules and requires approved updates
   to P02/P03/P04/P05, including `OOS-003`.
3. **DUAL_MODE — Dual-mode:** support both canonical text scores and JPG/PNG image scores,
   clearly distinguish their formats, define validation/storage/display rules,
   and update the approved requirements/architecture/scope artifacts.

Do not choose or implement a hybrid implicitly. If no decision is available,
stop before code changes, record status `BLOCKED`, and identify the exact
conflict. The prompt must preserve the supplied ACs as requested change evidence
without representing them as already approved upstream requirements.

## 7. Implementation Boundaries After Approval

### Included

- Authenticated score-create form and backend endpoint.
- Required title, instrument, description, and current-user ownership derived
  from the server session.
- Only the approved content mode(s) selected in Section 6.
- Server-authoritative field/content/file validation and actionable errors.
- Persistent score model and safe forward migration.
- Feed visibility through the existing feed if present, or the smallest
  documented integration needed for US-007; do not build the entire feed story.
- Focused backend/frontend tests, implementation artifact, and validation.

### Excluded

- Score edit/delete (US-005/US-006), complete feed/filter/pagination/detail
  workflows (US-007/US-008), likes/comments, OMR, audio, or unrelated features.
- Unapproved image storage providers or database blob storage.
- Destructive database reset, migration replacement, or rewriting upstream
  artifacts without explicit controlled approval.

## 8. Technical Requirements

### 8.1 Authentication, validation, and persistence

- Require the existing Django session and CSRF on publication mutations.
- Set publication owner from `request.user`, never a client-supplied owner ID.
- Validate all metadata and content on the backend; frontend checks are only
  usability hints.
- For canonical text mode, follow FR-006..FR-008 exactly: `.abc` or plain text,
  non-empty, at most 1,000 characters, and minimal ABC validation for `X:`,
  `T:`, `M:`, `L:`, `K:` plus a valid musical line. Do not add advanced ABC
  grammar requirements.
- For approved image mode, verify actual JPEG/PNG bytes, extension/content
  agreement, and an explicitly approved configurable size limit. Use Django's
  storage API; store a path in the database, not image bytes. Serve uploaded
  content with appropriate access control and safe content headers.
- For dual mode, implement and test both modes separately; unsupported PDFs
  must be rejected as specified.
- Ensure invalid submission does not create a partial publication or leave
  orphaned media files.
- Keep the score model/API extensible for US-007 feed consumption without
  coupling persistence to UI code.

### 8.2 Frontend

- Use a dedicated, replaceable score publication page/form and a small typed
  API helper, following the existing React/TypeScript structure.
- Show title, instrument, and description; show only the content control(s)
  authorized by the approved decision.
- Render field/content/file errors accessibly, preserve safe form data after
  failures, and show success/navigation only after persistence succeeds.
- Keep responsive layout aligned with NFR-002 and do not add a new UI/router
  dependency without justification.
