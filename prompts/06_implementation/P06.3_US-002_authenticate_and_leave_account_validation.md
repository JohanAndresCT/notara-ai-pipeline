## 4. Acceptance Criteria

| ID | Expected behavior | Required evidence |
|---|---|---|
| AC-US002-01 | Valid registered credentials grant access to the authenticated personal dashboard/home destination. | Backend login test checks session user; browser flow reaches authenticated destination and session endpoint confirms identity. |
| AC-US002-02 | Incorrect credentials show an error and do not grant access. | Wrong-password test verifies no authenticated session; UI displays clear generic error. Unknown email and wrong password must not reveal which condition occurred. |
| AC-US002-03 | Logout ends the session and redirects to public home. | Authenticated logout POST succeeds; session is invalidated; follow-up `/api/me/` is 401; browser lands in public state. |
| P02 AC-003 | Valid authentication information enables protected functionality. | Direct API/session test and UI flow. |
| P02 AC-004 | Logout prevents protected functionality without authenticating again. | Follow-up protected API request is denied and session is no longer authenticated. |
| P02 AC-005 | Invalid authentication does not grant access and returns a clear result. | Backend and UI invalid-credential tests. |

## 5. Detailed Review

### 5.1 Authentication correctness

- Test a user created through the existing registration flow or a controlled
  persisted test fixture.
- Verify correct email/password authenticates the same account and exposes
  only safe identity fields.
- Test wrong password and unknown email. Responses must be generic and
  equivalent in status/error content so they do not enable account enumeration.
- Verify missing/malformed request data returns a safe, clear error and does
  not establish a session.
- Verify anonymous access to `/api/me/` and the authenticated dashboard's
  protected data is denied or routed to login as designed.

### 5.2 Logout/session/security

- Verify logout is a CSRF-protected state-changing POST, not GET.
- Confirm Django server-side logout invalidates the session, clears/rotates the
  relevant session cookie as expected, and subsequent `/api/me/` returns 401.
- Confirm browser client state is cleared only after successful logout and
  failure is not represented as success.
- Confirm no plaintext password, password hash, session identifier, or auth
  token is logged, returned, or stored in local/session storage.
- Confirm no CSRF bypass, client-only authorization, or unrelated weakening of
  protected endpoints was introduced.

### 5.3 UX, navigation, and responsive behavior

- Verify login form labels, keyboard access, submission state, generic error
  display, and safe password handling.
- Verify successful login reaches the authenticated dashboard/home shell.
- Verify logout returns to public home, where login/register navigation is
  available, and authenticated controls are no longer shown.
- Verify mobile and desktop widths; record exact browser, version, viewport,
  procedure, and outcome. Target current Chrome, Edge, and Firefox at 360, 768,
  and 1280 px as available. Do not claim untested matrix cells.
- Keep full feed/dashboard functionality out of this story; validate only the
  authenticated landing shell and access boundary.

### 5.4 Implementation log and traceability

Ensure the P06.3 log entry matches actual code, migrations (if any), command
outputs, and browser evidence; traces FR-002/FR-017 and AC-003..AC-005; records
the `/api/` versus `/api/v1/` architecture path deviation; and leaves Product
Owner approval pending unless actual evidence is recorded.

## 7. Severity and Overall Result

- **CRITICAL:** unauthorized access, session not invalidated, credential
  disclosure, or material authentication bypass.
- **HIGH:** valid login/logout flow fails, invalid credentials grant access, or
  story criteria cannot be met.
- **MEDIUM:** material responsive, accessibility, traceability, or verification
  gap with a review gate.
- **LOW:** minor documentation or maintainability issue with limited impact.

Choose exactly one final result:

- **PASS:** all canonical and supplied criteria pass with evidence; invalid
  credentials do not leak account existence; logout invalidates server state;
  required verification is complete.
- **PASS_WITH_WARNINGS:** core criteria pass but non-blocking browser, database,
  architecture-alignment, or external review gates remain.
- **FAIL:** implementation exists but a material criterion or security check
  fails.
- **BLOCKED:** implementation is absent or a concrete environment/prerequisite
  prevents reliable validation.

Do not claim DoD completion while Product Owner approval is pending.
