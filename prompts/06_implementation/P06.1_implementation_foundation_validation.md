# P06.1 — Implementation Foundation Validation

**Version:** 1.0  
**Phase:** P06 — Implementation  
**Type:** Validation prompt  
**Execution mode:** Foundation review and evidence check

## 1. Objective

Validate whether the repository implementation foundation created from the
`P06.1_implementation_foundation.md` prompt is consistent with the approved
architecture, does not implement story-specific functionality, and is ready for
independent foundation review or progression to further incremental work.

This validation must assess the actual repository state, not merely the text of
an implementation plan or a generated log. It is a verification step for the
technical foundation stage.

## 2. Required Inputs

Read and use the following local project artifacts and current repository state:

1. `prompts/system/SYSTEM_PROMPT.md`
2. `prompts/06_implementation/P06.1_implementation_foundation.md`
3. `artifacts/05_architecture/ARCHITECTURE.md`
4. `artifacts/05_architecture/ARCHITECTURE_VALIDATION.md`
5. `artifacts/03_planning/PRIORITIZATION.md`
6. `artifacts/03_planning/product_backlog.json`
7. `artifacts/04_ux/UX_SPEC.md`
8. `artifacts/04_ux/UX_SPEC_VALIDATION.md`
9. The current repository structure, active source files, manifests, configs,
   environment settings, and any implementation log or configuration generated
   by the foundation step.

If any required artifact is missing, unreadable, or inconsistent with another
authoritative artifact, record the issue and determine whether validation can
safely proceed.

## 3. Preconditions and Blocking Conditions

Before validating the foundation:

1. Confirm the architecture document exists and is traceable to the approved
   source artifacts.
2. Review the architecture validation result for unresolved blockers or
   warnings that materially affect the foundation.
3. Inspect the repository state to determine whether the foundation exists,
   whether it is partial, and whether it should be extended rather than
   replaced.
4. Check whether the repository contains story-specific feature work that was
   added outside the approved foundation scope.

If the architecture is not approved, contains unresolved critical blockers,
or the repository cannot be inspected reliably, use `BLOCKED` and explain the
reason with evidence.

Do not silently assume that an unapproved design choice is valid.

## 4. Validation Boundaries

### 4.1 Included

Validate only the technical foundation necessary to support the approved MVP.
This includes:

- project structure and module layout;
- runtime and framework setup;
- application startup configuration;
- persistence and database connection foundations;
- security foundations and config handling;
- API or frontend foundation layers required by the approved architecture;
- environment variable handling and config examples;
- logging, exception handling, startup checks, and observability basics;
- implementation log sufficiency and repository traceability.

### 4.2 Excluded

Do not validate or endorse:

- individual user stories or acceptance-criteria behavior;
- story-specific features or business workflows;
- product-flow implementations that belong to future stories;
- seed data or mock behavior presented as actual application functionality;
- unapproved architecture changes or extra infrastructure.

If the foundation includes any story-specific functionality, record it as a
finding and determine whether it invalidates the foundation.

## 5. Validation Principles

Follow these principles throughout the review:

1. **Architecture conformance:** confirm the repository matches the approved
   architecture and document any justified deviation.
2. **Minimal sufficient foundation:** assess whether the foundation stays
   small, coherent, and suitable for incremental development.
3. **Repository truth:** validate against the actual files, configuration,
   package manifests, and runtime behavior in the workspace.
4. **Maintainability:** review whether the structure is understandable and
   supports future feature development without unnecessary complexity.
5. **Security by default:** verify no secrets, credentials, or sensitive data
   are committed or exposed.
6. **Traceability:** connect significant implementation decisions to the
   approved architecture and other authoritative artifacts.
7. **No invented requirements:** do not treat assumptions as product or
   technical facts without evidence.
8. **Evidence-first verification:** only claim checks passed if they were
   actually executed and documented with evidence.

## 6. Validation Process

### Step 1 — Inspect repository and source files

- read the project structure and all relevant local files;
- identify the implementation foundation files that were created or modified;
- confirm whether the repository already contained usable infrastructure;
- record missing files, blockages, or deviations from the documented
  foundation scope.

### Step 2 — Check conformance to architecture and scope

- verify the repository layout and tooling align with the architecture;
- confirm the foundation supports the approved MVP scope without adding
  unsupported technical complexity;
- confirm that story-specific functionality is not present unless it is a
  strict technical necessity for startup or verification.

### Step 3 — Validate configuration and startup foundations

Check, as applicable:

- project manifests and dependency configuration;
- framework/runtime configuration;
- module structure and app entry points;
- database configuration and persistence foundations;
- security configuration and secret handling;
- environment-variable patterns and example config files;
- logging, exception handling, and health check or startup verification.

### Step 4 — Validate implementation log quality

If `artifacts/06_implementation/IMPLEMENTATION_LOG.md` exists, confirm that it:

- reflects the actual repository state;
- describes what was implemented, what was not, and why;
- clearly distinguishes implemented foundation vs. story-specific work;
- records assumptions, unresolved issues, and verification results;
- includes execution instructions and limitations;
- marks status honestly as `READY`, `READY_WITH_ASSUMPTIONS`, or `BLOCKED`.

### Step 5 — Run relevant verification checks

Execute the available checks that are appropriate to the repository and
foundation, such as:

- dependency installation or dependency consistency checks;
- build or compile checks;
- application startup checks;
- database connection or config checks, if feasible;
- health checks or equivalent technical verification;
- any existing automated foundation checks.

Document the exact commands and outcomes. If a check cannot be run due to a
missing dependency, missing environment, credential requirement, or project
limitation, mark it as `NOT_RUN` or `BLOCKED` and explain why.

### Step 6 — Assess implementation risk and readiness

Determine whether the foundation is:

- ready to support incremental feature work;
- ready with documented assumptions or limitations;
- blocked by unresolved dependency or architecture conflicts;
- invalid because story-specific functionality appears in the foundation.

## 8. Severity Levels

- **CRITICAL:** Foundation is unsafe, materially inconsistent with the
  architecture, or prevents the project from starting or being reviewed.
- **HIGH:** Major requirement or architecture mismatch; the foundation cannot
  confidently support incremental development.
- **MEDIUM:** Material but bounded gap; the foundation is usable only with
  explicit assumptions or review gates.
- **LOW:** Minor documentation or traceability issue with limited product or
  technical impact.

## 9. Overall Result

Return exactly one result:

### PASS

The foundation is consistent with the approved architecture, contains no
material story-specific implementation, and is ready for further incremental
work or the next validation step.

### PASS_WITH_WARNINGS

The foundation is suitable for continued work but has non-blocking warnings,
assumptions, or review gates that must remain explicit.

### FAIL

The foundation has materially incorrect or incomplete architecture alignment,
startup/configuration issues, or story-specific behavior that should be fixed
before proceeding.

### BLOCKED

The repository state or architecture evidence prevents reliable validation.

4. Required human decisions or blockers.
